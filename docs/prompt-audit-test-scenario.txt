Kamu adalah Codex AI Agent yang bertugas melakukan FULL AUDIT terhadap proyek Portal Satu Data Bulungan.

Tujuan audit:
1. Menguji semua fitur, semua menu, semua endpoint, semua role, dan semua alur publik/internal.
2. Memastikan implementasi sesuai dengan kode nyata di repo, bukan asumsi.
3. Mencatat semua error, bug, inkonsistensi, celah keamanan, masalah akses role, masalah validasi, masalah UX, masalah performa, dan peluang optimasi.
4. Jangan memberikan test palsu.
5. Jangan menganggap sebuah fitur berhasil jika belum benar-benar diverifikasi dari kode, test otomatis, hasil runtime, atau bukti log/screenshot.
6. Jika fitur yang disebutkan dalam panduan tidak ditemukan di repo, tandai sebagai `NOT FOUND / NOT IMPLEMENTED`, bukan dianggap gagal secara asumtif.
7. Jika fitur ada di repo tetapi tidak bisa diuji karena blocker seperti credential/env/dependency, tandai sebagai `BLOCKED` dan jelaskan blocker-nya.

Konteks proyek:
Portal ini adalah Portal Satu Data Bulungan.

Mode sumber data:
- `mock`: data dibaca dari store lokal bersama `.local/internal-portal-store.json`.
- `ckan`: data dibaca/ditulis ke backend CKAN.

Konfigurasi utama:
- `DATA_SOURCE_MODE=mock|ckan`
- `NEXT_PUBLIC_CKAN_BASE_URL`
- `CKAN_BASE_URL`
- `CKAN_API_KEY`

Role aktif:
- `admin`
- `walidata`
- `operator_opd`

Tidak boleh mengasumsikan adanya role:
- `super_admin`
- `reviewer`

Hak akses role:
1. Admin:
   - Akses penuh modul internal.
   - Bisa semua transisi workflow.
   - Bisa ubah settings portal.
   - Bisa kelola users, roles, organisasi, topik, integrasi jika fitur tersedia di repo.
2. Walidata:
   - Fokus validasi, kurasi, publikasi lintas OPD.
   - Bisa `Submitted -> Need Revision`.
   - Bisa `Submitted -> Approved`.
   - Bisa `Approved -> Published`.
   - Bisa `Published -> Archived`.
   - Tidak diasumsikan bisa ubah settings kecuali kode membuktikan sebaliknya.
3. Operator OPD:
   - Bisa buat draft.
   - Bisa edit dataset miliknya sendiri.
   - Bisa submit/re-submit.
   - Tidak boleh approve, publish, archive.
   - Tidak boleh mengubah dataset organisasi lain.
   - Tidak boleh upload lintas organisasi.

Workflow dataset resmi:
- `Draft -> Submitted -> Need Revision -> Submitted -> Approved -> Published -> Archived`

Aturan transisi:
- `Draft` hanya boleh ke `Submitted`
- `Submitted` boleh ke `Need Revision` atau `Approved`
- `Need Revision` hanya boleh ke `Submitted`
- `Approved` hanya boleh ke `Published`
- `Published` hanya boleh ke `Archived`
- Semua transisi lain harus ditolak API/UI.

## 1. Discovery awal repo

Lakukan inspeksi awal repo sebelum menjalankan test.

Wajib:
1. Identifikasi framework, package manager, dan struktur folder.
2. Temukan semua route/page/API aktual dari kode.
3. Temukan semua komponen menu/navigasi publik dan internal.
4. Temukan definisi role/permission/middleware/auth guard.
5. Temukan seed user atau credential dummy yang tersedia.
6. Temukan konfigurasi env yang diperlukan.
7. Temukan script test/lint/build yang tersedia di `package.json` atau config lain.
8. Temukan adapter data untuk mode `mock` dan `ckan`.
9. Temukan store lokal `.local/internal-portal-store.json` jika ada.
10. Temukan semua validasi API, schema, middleware rate limit, origin check, honeypot, auth, dan authorization.

Output discovery:
- Buat daftar route aktual.
- Buat daftar menu aktual.
- Buat daftar endpoint aktual.
- Buat daftar role aktual.
- Buat daftar fitur yang ada.
- Buat daftar fitur panduan yang tidak ditemukan di repo.

Jangan langsung menguji berdasarkan daftar panduan saja. Selalu cocokkan dengan kode nyata.

## 2. Persiapan environment test

Lakukan:
1. Install dependency sesuai package manager repo.
2. Jalankan lint jika tersedia.
3. Jalankan typecheck jika tersedia.
4. Jalankan unit/integration test jika tersedia.
5. Jalankan build production jika tersedia.
6. Jalankan aplikasi lokal jika memungkinkan.
7. Uji minimal di mode `mock`.
8. Uji mode `ckan` hanya jika konfigurasi env dan CKAN tersedia. Jika tidak tersedia, tandai sebagai `BLOCKED`.

Catatan:
- Jangan menggunakan credential produksi.
- Jangan mengirim data ke CKAN produksi kecuali repo/env jelas menunjuk ke environment dev/staging.
- Jika tidak aman menjalankan test destructive, gunakan mode mock/local.

## 3. Format laporan wajib

Buat laporan akhir dengan format berikut:

### A. Executive Summary
- Status umum proyek.
- Jumlah test case: total, passed, failed, blocked, not implemented.
- Risiko terbesar.
- Prioritas perbaikan.

### B. Test Environment
- OS/runtime.
- Node/package manager version.
- Branch/commit hash.
- Mode data yang diuji: mock/ckan.
- Env yang tersedia/tidak tersedia.
- Command yang dijalankan.
- Hasil command: pass/fail dengan bukti ringkas.

### C. Route & Feature Coverage Matrix
Untuk setiap route/menu/endpoint:
- Nama fitur
- Lokasi kode
- Route/API
- Role yang boleh akses
- Status: tested/pass/fail/blocked/not found
- Bukti
- Catatan

### D. Test Case Detail
Setiap test case harus memakai format:
- ID
- Area
- Role
- Precondition
- Steps
- Expected Result
- Actual Result
- Status: PASS / FAIL / BLOCKED / NOT IMPLEMENTED
- Evidence: log/screenshot/response code/file reference
- Severity: Critical / High / Medium / Low / Info
- Recommendation

### E. Bug & Error Log
Untuk setiap bug:
- ID bug
- Judul
- Severity
- Repro steps
- Expected
- Actual
- Affected route/API
- Affected role
- Screenshot/log/response
- Dugaan root cause berdasarkan kode
- Rekomendasi fix

### F. Security Findings
Untuk setiap celah:
- ID security finding
- Severity
- Jenis risiko
- Endpoint/route terdampak
- Role terdampak
- Repro steps aman
- Dampak
- Bukti
- Rekomendasi mitigasi

### G. Performance & Optimization Findings
Catat:
- Bundle/build issue
- N+1 request
- API lambat
- Pagination bermasalah
- Fetch berulang tidak perlu
- Client/server rendering tidak efisien
- Tidak ada caching saat seharusnya
- Payload besar
- Error handling buruk
- Logging tidak aman/berlebihan

### H. Final Recommendation
Prioritaskan:
1. Critical security/data integrity.
2. Authorization/role bypass.
3. Workflow/status bug.
4. Public data exposure bug.
5. Form validation/API validation.
6. UX/data consistency.
7. Optimization.

- `POST /api/data-requests`.

## 16. Kriteria PASS

Sebuah fitur hanya boleh ditandai PASS jika:
1. Fitur ditemukan di kode.
2. Dapat dijalankan atau diverifikasi dengan test/log/runtime.
3. Actual result sesuai expected result.
4. Tidak ada error console/server fatal.
5. Permission server-side benar.
6. Tidak ada data internal yang bocor ke publik.
7. Evidence tersedia.

Jika tidak memenuhi semua kriteria di atas, gunakan FAIL/BLOCKED/NOT IMPLEMENTED sesuai kondisi.

Mulai audit sekarang dari discovery repo, lalu jalankan test secara sistematis sesuai skenario di atas.
